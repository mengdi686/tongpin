## 0. 为什么现在调研、但不接入

- 阶段2 一旦开放真人资料卡、站内沟通，就产生 UGC（昵称、简介、聊天文本、头像/照片）。微信对 UGC 是**强制**内容安全审核，没接基本一票否决（见 `docs/13` 第 5 节）。
- 内容安全接口需要**企业主体 + 微信认证**才能调用——这跟阶段2 的企业主体路径天然绑定。**阶段1 个人主体接不了，也不该接**（阶段1 无 UGC，这正是纯工具边界的技术原因之一）。
- 现在把方案定清楚，触发后不用临时现学、不会因"没接审核"被驳回；但**不采购、不接境外服务、不提前烧钱**。

## 1. 微信官方接口（首选，免费额度内够用）

| 接口 | 覆盖 | 调用方式 | 免费额度（单 appId，以官方为准） |
|---|---|---|---|
| `security.msgSecCheck` v2 | 文本（昵称/简介/聊天） | 同步，传 `openid`、`scene=2`、`version=2` | 文本约 4000 次/分、200 万次/天 |
| `security.mediaCheckAsync` | 图片、音频、视频 | 异步：提交拿 `trace_id`，回调结果放行/拦截 | 图片约 2000 次/分、20 万次/天 |

- 返回三态：`suggest = pass / review / risky`。
- `87014` = 内容违规，直接拦截；其他错误码按 `SEC_CHECK_xxx` 处理。
- **额度各来源口径不一**：有资料写文本每日免费 500 次，也有写百万级。以你提审时官方文档/后台实时显示为准，**不按本文数字做容量承诺**。

## 2. 先审后发设计（阶段2触发后实现）

```
用户提交内容 → 落库标记 pending（不展示）
             → 调 msgSecCheck / mediaCheckAsync
             → pass：置为可见；review：进人工复审队列；risky：拦截并提示
             → 接口失败/超时：保持 pending，绝不默认放行（"宁可显示审核中"）
```

硬性要求：
- 机审**不得**被本地关键词表或人工初审替代——平台规范明确禁止，人工只能作补充。
- 审核结论与风控台账落库留痕（`audit_logs` 已在 `docs/AI_HANDOFF` 数据模型中），**不存图片原图**（继承 `docs/08` 红线）。
- `openid` 传真实用户，否则判定会变粗。
- `access_token` 缓存复用（有效期 7200s），不能每次现换。

## 6. 重要修正：`/api/link` 当前只是"认领打标"，不是真归并（防踩空）

- `docs/13` 第 4 节写"按手机号把历史 events/profiles/result_snapshots/births 归并到新 user_id"——这是**触发后的目标设计**。
- 线上现状（`apps/stage0-api/server.py` 的 `/api/link`）：仅对 `reservations` 表 `UPDATE ... SET linked_at`，**没有任何跨表归并**，因为阶段2 的 `users` 表尚未建立，没有归并目标。
- 因此正确的阶段衔接是：
  1. 阶段0/1：手机号进 `reservations`；`/api/link` 只标记"该手机号已被认领"。
  2. 阶段2 建 `users` 表后：**新增真正的归并脚本/接口**，按手机号把历史 `vid` 下的 `events`/`profiles`/`result_snapshots`/`births` 归属到新 `user_id`，保留 `vid` 溯源。
  3. **绝不静默合并 openid**：仍须用户主动用手机号认领。
- 触发时必做：实现真归并逻辑并加入删除权 `TABLES`（见 `docs/08`），否则阶段2 用户看不到历史数据、删除权也漏表。此项已列入触发清单，不是现在改（现在建表会浪费且阶段1 用不上）。
