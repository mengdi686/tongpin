## 1. 阶段2 能做什么、不能做什么（与阶段1 的分界）

| 维度 | 阶段1（当前） | 阶段2（触发后） |
|---|---|---|
| 主体 | 个人 | 企业/个体工商户 |
| 类目 | 工具 > 信息查询 | 社交 > 婚恋交友 / 陌生人交友 |
| 资质 | 无 | ICP 许可证（增值电信业务经营许可证）、网络安全评估报告 |
| 身份 | vid + OpenID 锚点 | 手机号注册 + 实名核验；历史 vid 按手机号归并 |
| 核心功能 | 自测 + 结果 + 分享 | 真人资料卡、匹配推荐、站内沟通 |
| 生辰数据 | 仅文化彩蛋，不进排序 | 派生结果可作**弱权重展示标签**，仍不单独决定匹配 |
| 付费 | 无 | 会员/增值服务（需 ICP 证 + 支付资质） |
| 内容安全 | 无 UGC | 必须：先审后发、举报入口、人工值守、风控台账 |

**红线继承**：阶段0/1 的所有禁用词表、配对断言禁令继续适用。阶段2 也不得写"正缘概率""命中注定""某五行相配"——即使有了婚恋类目，命理断言仍是《互联网信息服务管理办法》与平台规范的高压线。

## 2. 数据模型骨架（触发后建表，现在不建）

以下表在阶段2 启用，字段设计已考虑与现有 8 张表兼容（同库 `/srv/tongpin-data/stage0.db`，新增表须同步加入 `store.py` 的 `TABLES` 元组，否则删除权会漏表）。

### 2.1 用户与身份

```
users
  id INTEGER PK
  phone TEXT UNIQUE          -- 注册手机号（来自 reservations / 用户主动注册）
  phone_hash TEXT            -- 检索用哈希，明文 phone 加密存 phone_enc
  phone_enc TEXT             -- Fernet 加密
  openid_enc TEXT            -- 阶段1 OpenID，触发后按手机号归并带入
  vid TEXT                   -- 源 vid，保留溯源
  realname_verified INTEGER  -- 实名核验状态（对接合规方案，不存身份证号）
  created_at / updated_at
```

### 2.2 画像与偏好

```
user_profiles
  user_id INTEGER PK
  resonance INTEGER          -- 阶段0/1 同频值，弱权重
  styles TEXT                -- 风格词 JSON
  care_top TEXT              -- 关系在意点 JSON（L2 四维）
  birth_elements TEXT        -- 派生五行分布（不存生日原文）
  day_master TEXT            -- 日主（弱权重展示标签）
  zodiac TEXT                -- 生肖（弱权重展示标签）
  preference TEXT            -- 择偶偏好 JSON（年龄区间/城市/关系节奏）
  updated_at
```

### 2.3 匹配与沟通

```
matches
  id INTEGER PK
  user_a / user_b INTEGER
  score REAL                 -- 综合分（见第3节）
  status TEXT                -- pending / accepted / rejected / expired
  created_at / decided_at

messages
  id INTEGER PK
  match_id INTEGER
  sender_id INTEGER
  content_enc TEXT           -- 加密存储
  risk_score INTEGER         -- 内容审核结论
  verdict TEXT               -- pass / review / block
  ts INTEGER
```

**不建**：人脸库、身份证号字段、精确地理位置字段、公开用户列表。

## 3. 匹配规则骨架（继承 docs/07 的科学边界）

设计原则（来自 Joel et al. 2017/2020，见 `docs/07` 第 1 节）：

- **个体特质权重低**：大五维度（L1）只作弱信号，不可作为主要排序依据——见面前的自陈特质对"这一对特有的吸引"预测力为 0。
- **关系内变量权重高**：L2 的承诺感、被欣赏感、冲突处理、关系节奏期待，解释关系满意度约 45%，是主要权重来源。
- **生辰派生结果弱权重**：日主/五行/生肖可作展示标签或破冰话题，**不得单独决定匹配，不得作为付费解锁项**。
- **不输出占比数字**：阶段2 推荐页不展示"同频 XX%"，该数字阶段0 专用（见 `docs/07` 5.1）。

建议权重（预研值，上线前需用真实数据校准）：

```
score = 0.55 × 关系节奏兼容度(L2) 
      + 0.25 × 明确偏好匹配(城市/年龄区间/关系节奏期待)
      + 0.15 × 风格相似度(L1，弱)
      + 0.05 × 生辰标签多样性(仅破冰趣味，非"相配")
```

**禁止**：把 `day_master`、`zodiac`、`elements` 做成"相配/相克"判断；把 `resonance` 写进推荐页卡片或算法输入。

## 4. 身份归并方案（阶段1 → 阶段2 的唯一正确路径）

沿用 `docs/09` 第 4 节与 `docs/08` 第 4 节的既定设计：

1. 阶段1 用户手动填手机号 → `/api/reserve` 写入 `reservations`（vid 关联）。
2. 阶段2 注册时用户填**同一手机号** → `POST /api/link {vid, phone}`。
3. 后端按手机号把该 vid 的历史 `events`、`profiles`、`result_snapshots`、`births` 归并到新 `user_id`。
4. **不静默合并 openid**：openid 只是锚点，必须由用户主动用手机号认领。
5. 归并后保留 `vid` 字段作溯源，删除权按 `user_id` 与 `vid` 双通道生效。

已预留接口：`/api/link`（见 `docs/08` 第 4 节），无需改代码，触发后接前端即可。

## 5. 合规路径（触发后并行启动，周期是实际瓶颈）

| # | 事项 | 估算周期 | 备注 |
|---|---|---|---|
| 1 | 企业主体或个体工商户注册 | 3–10 工作日 | 经营范围含"第二类增值电信业务" |
| 2 | ICP 许可证申请 | 30–40 工作日 | 纯内资、注册资本≥100万、3人社保、境内服务器 |
| 3 | 小程序备案变更（主体变更） | 1–20 工作日 | 个人主体不能升级，需新注册企业小程序 |
| 4 | 婚恋交友类目申请 | 1–4 周，可能反复 | 需 ICP 证；各地口径不同，先书面确认 |
| 5 | 实名核验方案 | 1 周 | 对接合规服务商，**不存身份证号原文** |
| 6 | 内容审核 + 举报 | 1 周 | 先审后发，保留审核日志与风控台账 |
| 7 | 个人信息保护影响评估（PIA） | 1 周 | 生辰/人脸若启用需做，报告留存 3 年 |
| 8 | 安全评估报告 | 20 工作日 | 具舆论属性服务需在公安平台填报 |

**顺序依赖**：1 → 2 → 4 是主链，5/6/7 可并行。任何一步未完成不得提审。
